Redis 模式下和桥通信的链路

请求怎么进 Redis 有两条路（队列 / 订阅频道）；回包三处同写；服务端再按方法分派到三条执行路；另有一条只推不调的推送路。

链路① 队列路 —— 支持的 RPC：全部

客户端侧入口就是 xtdata.* / xt_trader.* 兼容层，底层都是 RPUSH + BLPOP。

链路② 订阅频道路 —— 实际支持：0 个

传输层能装同样的信封，方法集名义上与链路①一样，但两个硬条件让它现在没法用：

  1. 服务端只有 rpc_background_threads=True 时才起 _listen_loop 订阅 bigqmt:rpc:req:{账号}；drain 模式（0.3.51+ 默认）下 start_receiving(background_threads=False) 直接返回、不起任何收包线程，而 drain_request_queue 只 LPOP 队列 —— PUBLISH 进去的请求永远没人取，客户端一路等到超时。
  2. 客户端必须显式 call_redis_rpc(..., transport="pubsub")；仓库里没有任何调用方，只剩 parity 分支和测试。
结论：别用链路②。要"请求立刻被取走"，改 rpc_background_threads: True（走的是同一个 list，仍是链路①），不是切到频道。

回包 —— 不是独立请求路，但服务端固定写三处

写哪键谁等它
RPUSH listbigqmt:rpc:respq:{acct}:{rid}BLPOP —— 默认客户端
SETEX string（60s）bigqmt:rpc:resp:{acct}:{rid}GET —— BLPOP 超时兜底
PUBLISH channelbigqmt:rpc:resp:{acct}:{rid}pubsub 客户端订阅

三个写操作合并进一条 pipeline（#343）：分开发的话每一条都要跨线程重新抢一次 GIL，一次回包要付约 8 个 adjust 拍。

链路③ 推送路 —— 只推数据，不接受 RPC 调用

频道 / stream送到哪个回调
bigqmt:order_events:{acct}on_stock_order
bigqmt:trade_events:{acct}on_stock_trade
bigqmt:order_error_events:{acct}on_order_error（含 #345 的影子结算拒单）
bigqmt:cancel_error_events:{acct}on_cancel_error
bigqmt:quote_push:{acct}:{topic}subscribe_whole_quote 的行情数据（topic = exec:order / exec:trade / …）

exec 四路是 XADD（stream，maxlen≈2000，可短时重放）加 PUBLISH，两者同名。注意 subscribe_whole_quote / unsubscribe_whole_quote / quote_keepalive / quote_unsubscribe_all 这 4 个是普通 RPC，走链路①；链路③只出数据。
